# Worker 战斗计时修复

## 已确认的问题

2026-10-04 线上诊断（无浏览器渲染或素材加载的自建单人局）中，30.05 秒真实时间只推进 39.5 秒战斗时间，约 1.314 倍，而配置为 2 倍。该样本不是所有对局的速度保证，但足以证明服务端逻辑时间会落后，不只是画面插值。

旧 WorkerFieldRunner 将累积时间限制在 9 tick，并在派发超过 8 tick 时丢弃剩余时间。2 倍速时每个 8-tick 工作轮次覆盖约 133 ms 的真实时间；实际丢弃判断在累积达到 9 tick（约 150 ms）时触发。Worker 排队、回包等待或主线程卡顿会触发它。原单线程 runner 也有防追帧积压的丢弃策略；异步 Worker 又增加了往返等待，不能照搬该策略。

因此，整机有空闲核不代表模拟必然实时：主线程处理回包前，当前池中的同一 Worker 不会收到下一个队列任务。CPU 平均占用低于 100% 也不排除短时主线程满载、调度等待或事件循环停顿。

## 修复边界

- 保留活跃时间债务，只扣除已经派发的 tick，不再因跨过 8 tick 就清零。债务是一个数值，受本阶段剩余 HARD_CAP_SECONDS 约束，不生成无界任务队列。
- 每次 FIFO 工作轮次最多 32 tick，约 1.067 战斗秒；工作预算与时间债务分离。收到有效回包后，可立即派发下一轮有界工作，不必再等一个 33 ms 定时器。
- 大于正常 8 tick 的追赶批次只传每个 field 最后的完整 snapshot/meta，保留每条原始 event wire、其原始 gt、spawn UnitInfo、所有数值 effects 和完整结果。不跳过模拟步骤、不重写事件时间。
- 每阶段一个在途命令、每 Worker 的原 FIFO、boss 同阶段共享 HP/LP、退出/取消/旧代次隔离、最终结算一次的契约不变。
- 暂停仍保持既有语义：在途回包暂存，恢复时只接收一次并重置真实时钟/未派发债务，不补算暂停期间时间。显式暂停恢复的重置是有意行为，不是负载下的静默丢时间。
- 单线程、VirtualScheduler、自定义 BattleClass、前端和协议均不变。

## 验证与已知限制

专门回归覆盖 50/100/150/300 ms 命令延迟、3 秒主线程停顿后追赶、公平轮次、hard cap、暂停/resync、旧阶段隔离，以及 normal/unite/boss/hidden 的完整结果、事件和 effect 一致性。控制样本中原实现会丢失的 1200 tick 预算被完整保留。

本机真实服务+6 Worker+双浏览器在每秒人为阻塞主线程 180 ms 时，通过渲染、刷新重连、结算和下一回合。独立 WebSocket 样本推进 35.533 战斗秒/17.732 真实秒，约 2.004 倍。此结果不能直接当作线上相同负载下的性能承诺。

**这不是主线程性能优化的终点。** 主线程仍承担房间/经济/准备阶段/机器人试算等工作，池仍有确认链路。如果持续服务周期或 CPU 开销超过容量，时间债务仍可能增加，客户端仍可能卡顿或短暂追赶；修复不再永久丢失这段时间，但不承诺任意负载都能实时。需要继续通过 profile 确认热点，再考虑缓存、减少视图重建、低优先级 Worker 试算或房间分片。

此文和提交不代表游戏已经上线修复。游戏进程内保存对局，部署这份游戏代码需要另行确认窗口；静态资源服务的热更新授权不能当作重启游戏的授权。
