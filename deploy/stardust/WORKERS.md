# 固定战斗 Worker 池

## 范围和配置

运行时仍是 Node 原生 HTTP/WebSocket、一个房间管理进程，也不改变浏览器协议；唯一的外部存储是可选的对局存档 Valkey（`SP_REDIS_URL`，见 [docs/DEPLOY.md §11](../../docs/DEPLOY.md#11-断点续玩重启后接着打可选valkey)），不设就没有。`SP_COMBAT=server` 下，普通战斗、联防、最终决战及隐藏核心的实时演算可移入 `worker_threads`。

配置示例（不是部署状态或容量结论）：

```yaml
environment:
  SP_COMBAT: server
  SP_VERIFY: "off"
  SP_COMBAT_WORKERS: "6"
```

- 本地显示副本（2026-10-12）：Worker 演算的普通战场/联防默认以 `b.start { local: true }` 交给声明了 `g.sim { local: true }` 的本人浏览器本地演算显示，Worker 每 2 游戏秒发送状态摘要 `b.sync`，摘要或结束帧不一致、加载失败或设备过慢时该浏览器回到 `b.snap` 推流。结果、层数、LP、伤害榜与结算仍只取 Worker。`SP_LOCAL_REPLICA=0` 关闭（需重建游戏角色才生效）。观战、观众席与 Boss/隐藏核心战场保持推流。
- `SP_COMBAT_WORKERS` 默认 `0`：保持原单线程实现。接受 `0..32` 的整数，格式错误在监听端口前报错。
- `SP_VERSION_COMBAT_WORKERS` 默认 `2`：历史版本子进程各自的战斗线程数（协调器 `combatWorkers: 0` 只管它自己的进程）。这些线程在协调器容器里，算进它的 `pids_limit`；`0` 退回子进程主线程内联演算和推流。
- rel26 起集群把历史版本对局放到 game 节点（`SP_VERSION_PLACEMENT`，默认 `node`；`coordinator` 退回上一行的协调器子进程）。
  game 节点上：`SP_NODE_VERSION_HOSTS` 默认 `1`（同时最多几个版本子进程，`0` = 只跑第二期下半），`SP_NODE_VERSION_COMBAT_WORKERS`
  默认 `1`（每个版本子进程的战斗线程）。子进程和它的线程都在 game 容器里，算进 game 的 `pids_limit`（128）和内存。
- 固定池由服务器启动时创建、Lobby 注入每个 Match；线程被全部房间共用，不是每个房间创建线程。
- 一整个战斗阶段的所有 field 始终在同一个 Worker，包括共享 Boss HP、团队 LP、超时扣血和同 tick 的结束顺序。不同阶段可重新分配。
- 虚拟时钟、自定义 BattleClass、客户端权威战斗及其验证/接管仍走原路径。准备阶段预览和机器人布局试算也仍在主线程；不能把这一改动理解为整个游戏逻辑全部并行。
- `maxRooms` 是内存房间数量的准入设置，不是同时演算容量承诺；默认值与0=unlimited语义按所选runtime核对。认证、协议、每socket和Worker执行背压不因池数量而放宽。

## 数据与生命周期

每个 Worker 在启动时安装一份完整、深冻结的数据集，然后再加载模拟模块。线程内所有阶段复用同一个数据源和派生缓存；不在每个命令前切换全局数据，也不为每局复制整份游戏数据。

Match 保留玩家经济、授权观察者、阶段状态机和最终结算。Worker 只持模拟对象并返回数据：当前进度、事件/快照/动态元数据、完整结果、诊断记录以及 Boss/LP 变化。直播帧在 Worker 中编码为原协议 JSON，同一帧可直接发给多个有权限的观察者，避免主线程反复复制对象树/编码；沿用原 WebSocket 背压规则，仅 `b.snap` 可丢弃。结果重放仍走原路径。内部结算结果不经过浏览器结果的裁剪函数，`synthetic`、`unitStats` 和 `unspawned` 都保留。

- 全局唯一会话代次、线程代次和命令序号隔离旧房间/旧回合的迟到消息。
- 每个阶段最多一个命令在途；每个线程最多一条 MessagePort 消息在途。一条消息可以是一个批次：同一线程队列里不同阶段的战斗命令（每阶段最多一条，最多 64 条）按 FIFO 顺序一起发出、逐条执行、一次回包；清理和试算命令不进批次，战斗 FIFO 仍优先。总会话与请求队列有界。
- 实时（RealScheduler）阶段不再各自建 33 ms 定时器，而是挂在池的同一个 33 ms 节拍上：同一拍内所有阶段先计算推进量，再按线程各发一个批次。时间债务、每轮 32 tick 上限、暂停/恢复和回包后立即续派都不变；自定义/测试调度器仍用自己的定时器。
- Worker 的直播回包按需携带字段元数据：进行中的帧只给待重同步的字段（单人模式可暂停，始终携带）附带 `m.field` 元数据，state 回包和已结束字段始终携带；不含共享 Boss 池的已结束字段只发一次终局帧和结果，主线程用缓存的终局快照继续按 1 秒节奏重发。Worker 内回包不再额外 structuredClone（postMessage 本身同步复制）。
- 暂停后，在途回包暂存，不发布帧、不修改镜像状态、不触发结算；恢复时接收一次，重置真实时间累计，不补算暂停时间。
- 无已连接观察者时不生成直播快照。重连请求当前动态元数据和快照，不能永远复用开局 metadata。观察者离线/切场后的重同步请求会清理，避免阻塞演算。
- `forceField/forceAll` 产生最终结果；取消/关闭只销毁会话，不结算。完成、退出和取消后的迟到消息不再修改 Match。
- 正常关闭服务器会取消全部会话并等待线程终止。`SP_COMBAT_WORKERS=0` 可回退，但更改该值需要重建/重启游戏，不能保留进程内对局。

## 故障策略

启动线程失败会使服务器启动失败，而不是带着假就绪状态接收玩家。运行中线程崩溃/超时会通知其拥有的全部阶段（包括当时没有在途命令的阶段），**中止这些对局并明确记录 `reason=error`**；不会从展示快照假装恢复，也不会用合成胜利或虚构超时扣血结算。已经进入隐藏核心的对局保留此前的基础胜利，但不会伪造隐藏核心通关。

崩溃线程完全退出后再尝试替换，每个槽位一生最多替换三次，使用退避，避免无限重启。其他线程拥有的阶段不受该线程故障影响。这是故障隔离，不是持久化容灾；服务器整体重启仍会丢失所有内存房间。

`/healthz` 增加 `maxRooms` 和 `combat`：配置/存活/就绪 Worker 数、会话数、待处理/排队/在途请求、待清理会话、替换次数。通过回环健康接口观察；不要为了方便把受保护的业务接口或源代码公开。

## 本地性能验证入口

可复现的饱和测试工具：

```sh
node tools/combatbench.mjs --workers=0 --sessions=24 --ticks=600 --batch=6
node tools/combatbench.mjs --workers=1 --sessions=24 --ticks=600 --batch=6
node tools/combatbench.mjs --workers=2 --sessions=24 --ticks=600 --batch=6
node tools/combatbench.mjs --workers=4 --sessions=24 --ticks=600 --batch=6
```

同一批 24 个重型战场（每场 70 个敌人、10 个干员），包含直播快照、线程传输和原协议 JSON 编码；0 Worker 使用原始 FieldRunner，不拿带 IPC DTO 复制开销的进程内 Engine 代替旧后端。预热不计时，比较完整终局结果 SHA-256。工具不访问任何生产服务。

比较时同时记录完整结果哈希、协议字节、吞吐、主线程与总CPU、事件循环延迟、RSS及线程数量。IPC会增加传输成本，更多Worker不保证更快，也可能提高总CPU和内存。受控fixture不是生产容量、房间上限或端到端延迟证明；只有实际执行的检查才能在私有记录中标为完成。
