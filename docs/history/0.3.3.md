# DESIGN §36 — 0.3.3

Part of [DESIGN.md](../DESIGN.md)。0.3.3 于 2026-10-25 作为 0.3.2 的热修复发布（released 2026-10-25），仅包含 round53 的商店装备空栏、满整备区互换与跨版本图标缓存三项修复。

## 36. 0.3.3

### 36.1 第一期商店装备核查与空栏显示（round53 shopequip，2026-10-25）

维护者在 0.3.2 的第一期游玩中报告「商店一直没有装备」，并确认官方第一期会出售装备。本次接受这条
亲历事实，以对应时期的官方表确定开放等级；没有将第二期的开放等级移植给第一期。

#### 复现结论与修正范围

对 `act1autochess`、`act1autochess@V1_1`、`act2autochess@V2_1` 的全部大厅模式（单人／四人 ×
标准 FUNNY／险境 NORMAL／绝境 HARD）各从 1 升至 6 级，升级后主动刷新，每名玩家购买装备。
在改动前即得到下表结果：第一期两个版本都在 5–6 级正常出售，第二期上半在 1–6 级正常出售。
本次没有复现「满足等级并刷新后仍永远没有装备」，不能把它宣称为已找到根因的服务端缺货问题。

确认的客户端问题：`shopBar.js` 按现存卡片的 `kind` 划分两栏，把所有 `null` 都当干员空位；第一期
4→5 级新增的装备位恰好是 `null`，因此跑到干员栏，装备区则错误显示 `SOLD OUT / 已购买`。
1–4 级根本没有装备位时也显示「已购买」。修正为服务端 `m.private.shop.layout` 发送实际干员／装备
位数，客户端据此定位空栏；装备位打开而未刷新时使用现有「空栏位：刷新或下回合开始时补满」提示，
未开放时不画售罄卡。已购买的真实装备仍显示「已购买」。抽取、库存、价格、升级后不自动补货的规则不变。
旧存档／mock 没有 layout 时仍按卡片种类推断（兼容处理；[ASSUMED]，无法恢复旧帧中 `null` 的原始种类）。

### 36.2 满休整区互换回归（round53 benchswap，2026-10-25）

维护者在第一期的 0.3.2 游玩中报告「休整区满的时候没法把休整区的干员跟场上的互换了」。
本次指令明确要求所有版本都允许不增加占位的互换，并保留真实新增卡片／部署的容量限制。

`server/match/player/placement.js` 在手牌／临时区→场上占位、场上→手牌干员这两个分支中，

就返回 `HAND_FULL`。第一期两个 profile 均写入 `benchFullSwap: false`，第二期两个版本没有此限制。
客户端 `canPlace` 已按交换后的占位数判断，并没有相同的第一期限制；故可拖入并确认朝向，却被服务端拒绝。

### 36.3 跨版本装备贴图与渲染查表缓存（round53 iconcache，2026-10-25）

#### 复现与根因

维护者报告：第一期下半玩过一局后切到默认第二期下半，商店的「见钱眼开玩偶」图标正常，购买后整备区却
显示「迅捷作战粮」。用真实版本 host、Chrome 和 Pixi 渲染器在同一页面内复现；反向切换也复现。
购入后的 `ItemView.info.icon`、商店和详情的图片地址已经正确，但整备区贴图的 canvas 像素仍是上一版。
回归在修正前双向均失败，因此不能只用「URL 已更新」作为验收。

来源：`data/items.json` 与 `data/versions/act1autochess/items.json`（§36.1 所列官方表的构建产物）。
两个版本的 `chess_item_2_07_e_a` 分别指向 `trap_1116_acarm116`（见钱眼开玩偶）和
`trap_1051_acarm051`（迅捷作战粮），同为 2 阶；`chess_item_2_01_e_a` 也分别是「不屈弹射器」和
「歌利亚头盔」。装备 ID 是版本内的记录键，不能当跨版本图片身份。

根因在 `public/js/render/units.js` 的 `ItemView`：把 `defId` 交给 `render/textures.js` 的
`itemTexture`。后者的模块级 `_items` 缓存贯穿页面生命周期，键为「调用者的 key、是否有图、边框色」；
相同 ID、阶级及加载状态直接取回旧 canvas。商店、详情和已装备的小图标没有走这条错误的 ID 缓存路径。

### 36.10 策略选择改为同时自由选择（维护者 2026-11-05）

维护者原话：「把策略选择改成额定倒计时，玩家可以同时自由选择策略，选择完成之后还可以取消选别的策略。倒计时结束则固定所选择的策略」。
有两名及以上真人博士的同盟模拟（`MatchPhases.freeDraft`），策略选择不再轮流进行，所有座位同时选择：

- **流程**：整个步骤只有一个 50 秒倒计时（`BAND_TURN_SECONDS`）。点「选择」先占住一个策略（`g.bandHold`），锁定前可以改选别的，
  也可以「取消选择」（`g.bandCancel`）。点「锁定选择」（`g.bandLock`）后策略、初始生命值就定下来，不能再改。没有跳过。
- **维护者的决定**：
  - 不能重复，先到先得。被队友占住或锁定的策略显示「已被选择」，队友取消后立刻放出来。扩容房照旧可以重复。
  - 倒计时统一 50 秒。
  - 所有博士都锁定就提前进入下一步；倒计时结束时，各人当前占住的策略直接固定。
- **实现时定的规则**（维护者未指定）：
  - 单人模拟和只有一名真人的同盟（`soloUntimed`）不变，仍是不限时的轮流选择。
  - 倒计时结束时什么都没占的博士（包括掉线的），按原来的超时规则分配：高亮的策略，否则华法琳，否则第一个空着的，按选择顺序依次分配，不会重复。
  - AI 座位照旧：房主指定的策略照用，其余立即锁定；开了「AI 队友最后选择」，就等所有真人锁定（或倒计时结束、真人都固定后）再选。
  - 中途退出的博士保留它占住的策略，什么都没占就分配默认策略。转为 AI 托管的博士，由 AI 直接锁定它占住的策略。掉线但还没被 AI 接管的博士算「仍在决策」，不会让步骤提前结束，倒计时到了照常固定。

  - 旧页面没有这个流程，看到的是「所有博士同时选择」（`concurrent`），点「确认选择」发 `g.band`，服务器把它当作占住并立即锁定。
  - 更新前存下的检查点（轮流选择）恢复后，仍按轮流选择进行到底。新检查点保存占住和锁定的状态，恢复后倒计时重新从 50 秒开始。
  - 外部 AI 在同时选择时也能拿到选策略的动作（`aiDigest`）。

  `g.bondPlan { bondId?, subIds? }`，`m.public players[].bondPlanSub`（没有时省略）。选择窗口先在本地选好，点「确认」一次发出；
  「清空选择」只清本地选择，确认后才生效。显示时主盟约在前（带名字或分隔线），副盟约是小图标。

  这个冷却不进检查点。确认本局信息和选择策略期间的修改不广播（预选在策略选择界面的名片上本来就看得到）。
- **禁用标注**：预选窗口的卡片对两种盟约标「盟约禁用」：模式本身不激活的（标准模拟的 10 个，卡片写「不会激活」），和本局随机抽中的
  禁用集合 D（确认本局信息里变灰的那些，卡片写「N 名干员无法出现」）。提示文字沿用确认本局信息的说法。选择策略时，本家盟约在这两种
  里的策略在卡片上标「X盟约禁用」（如「拉特兰盟约禁用」，两个就写「拉特兰、阿戈尔盟约禁用」），详情里照旧提示「本局禁用【拉特兰】盟约，此策略效果可能无法发挥」（`gameLogic matchOffBonds` = 静态 ∪ D）；以前只看静态的，所以险境以上难度从来不会标。
  仍然可以选。维护者指出「不应该显示本局禁用，可能导致歧义」（读起来像策略本身被禁用），所以两处卡片都写明是盟约禁用；策略墙上的标签改成红底白字（一行放不下时在盟约名和「盟约禁用」之间折成两行，两部分都完整显示），头像压暗（选中或已暂选时压得轻一些），扫一眼就能看出来；被队友选走的卡照旧按「已被选择」变灰。
  商店、盟约栏、详情卡里的「本局禁用」仍然只指模式不激活的盟约，因为 D 里的盟约还能通过多盟约干员激活。
- **商店高亮**（维护者选「自己的高亮 + 队友的标记」）：商店和晋升奖励里的干员卡，盟约含我的主盟约的，整张卡加粗的薄荷绿描边；
  只含副盟约的，描边细一些；卡上属于我预选的盟约标签也会点亮。和我共用卡池的存活队友，如果预选里有这张卡的盟约，就在卡片右侧显示他们的
  小头像（最多 2 个，再多显示 +N）。扩容房按 `poolGroups` 只算同一个卡池的队友；关了共享卡池的房间不显示队友。
- **兼容**：旧页面发的 `g.bondPlan { bondId }` 只改主盟约，副盟约保留（新的主盟约如果在副盟约里就去掉）。新检查点保存副盟约
  （`bondPlanSub`）；rel33 的检查点没有这个键，恢复后副盟约为空、主盟约不变。回滚到 rel33 时，它恢复本版检查点会忽略不认识的键
  （只丢副盟约），`SNAPSHOT_VERSION` 不变。没有规则、AI 或计时读取预选。

### 36.12 开局两屏尽量不滚动（维护者 2026-11-05）

维护者原话：「另外需要优化进入阶段，选择策略阶段的UI大小，尽量不用滚动」。界面的布局根 1rem = min(屏宽 / 19.2, 屏高 / 10.8)，所以宽度不小于 16:9 的屏幕，可用高度都是 10.8rem。下面的尺寸按这个高度在默认文字大小「小」下设定。

- **确认本局信息**（`screens/briefing.js`，`css/screens/briefing.css`）：
  - 原来是一列从上往下排，要滚动。现在分成两列：左列「本局遭遇敌方」在上、「核心盟约」在下；右列「附加盟约」（含图例）在上、「本局禁用干员」在下。
  - 内容和顺序都不变，各项缩小了：
    - 标题栏 .66 → .52rem；领袖头像 2.3 → 1.6rem；特训敌人图标 1.12 → .8rem，排在领袖下面一行；
    - 盟约圆标 1.1 → .7rem，核心 8 个一行，附加 15 个两行；
    - 禁用干员头像 1.2 → .62rem，与本局信息弹窗一样。
  - 「重刷本局」和「自选上场」所在的 `brief__dock` 移进底栏，放在左侧，与「已就绪」「准备就绪」同一行。底栏本身也从叠在内容上的绝对定位，改为在正常布局中占一行。
  - 页面本身不再滚动。某一列仍放不下时（短屏手机、大号文字、领袖说明特别长），只在这一列内部滚动。
- **选择策略**（`screens/bandDraft.js`，新文件 `ui/fitGrid.js`，`css/screens/draft.css`）：
  - 策略墙原来固定每行 4 个，每个 1.9rem，40 个策略要滚两屏多。现在会量出墙的空间，选能让所有策略都放下的最大尺寸和列数（`fitTiles` 写入 `--dcols` / `--dtile`）：
    - 最大 1.9rem，最小 .9rem，小于 .9rem 才改为滚动；
    - 1920×937 下排成 8 列，每个约 1.4rem；16:9 下排成 7 列，每个约 1.2rem；点开详情时也会重新计算。
  - 顺序列表的每行高度也按空间自适应（`fitRowHeight` 写入 `--drh`，范围 .96–1.26rem），行里的策略框和头像跟着缩放。4 人局正好放得下；扩容房 8–20 个座位放不下时，列表在内部滚动。
  - 没有 ResizeObserver 的浏览器保持原来的尺寸。
- **本局信息弹窗**：屏幕宽度允许时加宽到 20rem，各块之间的间距收紧。手机上仍按原设计在弹窗内滚动。
- 测试：`test/ui/draft-fit.test.js`（尺寸计算和接线）；`test/ui/ui-leftovers-3533.test.js` 两条钉住旧样式的断言已改为新规则。

### 36.14 匹配成功确认页：全屏动效与音效（维护者 2026-11-05）

维护者原话：「匹配到人之后需要添加动效和音效。重写现在的静态确认页面」。公开匹配凑齐人后（`queue.state` 为 `offered`），原来是右栏里的
静态面板。第一版改成右栏的动画面板，维护者看了说「感觉有点小丑」：太小，也不好看。要求改成全屏，并「可以整体参考瓦洛兰特（无畏契约）和
卡拉比丘的匹配成功之后的动效&页面」。参考只取这类画面的通用手法（大标题砸下、色块开合、竖条座位依次亮起、大号倒计时），画面、形状、
字体、配色、音效都是自己做的，用本作的薄荷绿配深色底和 lobby.css 的字体。

确认页现在是盖住整个屏幕的接管层：`ui/matchOffer.js` `OfferTakeover`，样式 `css/screens/match-offer.css`。它挂在 `main.js` 的 `App`
根上，所以不管下面是大厅的「同盟集结」、好友小队房间的匹配层（`screens/room.js`）还是别的对话框，都盖在最上面（z-index 77：
在各种页面和连接提示之上，在弹窗和 toast 之下）。原位置的 `QueueFlow` 只在它下面放一个「搜寻成功」占位。

- **出现**：背景变暗并模糊，铺一层细网格和扫描线，粒子向座位行飘近。一块薄荷色色块从中间横向弹开，中间有故障线，接着收拢成粗体大标题
  「匹配成功」，标题从放大状态砸下来，整体抖 2 px，时间和到达音效的撞击声对齐（`OFFER_RISE_S`）。上方的斜角小标签写着
  「队友已集结 · PUBLIC MATCHMAKING」。
- **座位**：每个需要的博士一个细长竖条（`required`）。桌面上始终一行，20 人是一行窄条；手机上超过 8 人分两行。入场时上下错开，
  波浪式依次落定。第一个是自己：用这台浏览器选的名片底图和头像（`ui/playerCard.js`），标「你」并加外框。其余是暗色剪影。
  有人确认时，对应竖条闪成亮白薄荷色，外框高亮一下。服务器只给人数，不给是谁，所以按顺序点亮。
- **倒计时**：座位下面是大号数字，再下面一条细进度条随确认时间缩短。全程按这台页面第一次看到这个匹配时的剩余时间算，重新挂载不会从头开始。
  还没确认时，最后 5 秒数字和进度条变成琥珀色并跳动。
- **按钮**：「确认入场」紧挨在数字下面，宽、主色，有缓慢的光晕和扫光。打开时焦点就在这个按钮上，按回车或空格就能确认。确认后这里换成
  「剩余 N 秒 · 等待其他博士」。「退出本次匹配」是下面一个低调的按钮，取消失败后变成「重试取消」。
- **信息**：底部一行小标签：难度、「N 名真人 · 不自动补 AI」、好友小队人数、规则摘要和「完整规则」链接。原来面板底部的匹配规则说明放进了「完整规则」对话框。
- **全员确认**：确认人数满了，或服务器开始准备对局（`allocationPending`）时：竖条依次闪亮，色块再开合一次，标题换成「搜寻成功！」，一个线稿
  徽记（八边形里一座塔）一笔一笔画出来，同时显示「全员已确认，正在连接游戏节点」。进入房间后这一屏再停 0.8 秒，然后淡出。
- **匹配未成立**：有人退出或超时时，标题变红，写「本次匹配未成立」，显示服务器给的原因，竖条往下掉。如果自己已确认，会回到等待队列；
  没确认的会被移出匹配。这一屏停 1.7 秒，然后反向擦除关闭。自己点「退出本次匹配」时直接反向擦除关闭。
- **减少动态效果**：系统设置或 `sp-reduced-motion` 开启时，什么都不动，也不停留；只有「本次匹配未成立」照样停 1.7 秒，因为要显示原因。
- 匹配结束后的这几个停留画面由一个跟着 store 走的状态（`installOfferStage`）决定，所以下面的页面切走了也不影响。

音效由 `ui/offerCues.js` 统一处理：只在 `main.js` 装一个监听，所以在哪个界面都会响，也不会因为重新渲染、重新挂载或重连后服务器重发同一个
`offerId` 而重复。音效全部用代码合成（`ui/offerSynth.js`），经 `audio.synth` 走音效通道，静音和音效音量设置都照常生效，不需要额外的音频文件：

| 时机 | 音效 |
|---|---|
| 新的匹配（新 `offerId`） | 上升的噪声扫频接一记撞击（低频下坠、噪声爆音、高频一响），撞击和标题砸下同时 |
| 其他博士确认（`acceptedCount` 增加，不含自己） | 清脆的双音「嗒」 |
| 自己的确认到达服务器（`accepted`） | 一声闷响，上面叠一个上行五度 |
| 还没确认时最后 5、4、3、2、1 秒，每秒一次 | 干脆的木质「咔」 |
| 全员确认（`allocationPending`、人数满，或先收到 matched） | 呼啸声（带通噪声扫上去再散开），底下一个轻的低频 |
| 匹配未成立 | 下滑的音加一声低沉的闷响 |

浏览器切到别的标签页时，音频原本会挂起（`AudioManager._onVis`）。现在有匹配时用 `audio.keepAwake('offer')` 保持运行，所以在别的标签页
等匹配也能听到提示。这时只有音效通道出声，音乐和语音静音，回到页面或匹配结束后恢复原样。
